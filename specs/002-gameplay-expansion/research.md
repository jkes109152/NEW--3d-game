# 技術研究：糖果風防空守衛改版

**日期**：2026-09-06　**分支**：`002-gameplay-expansion`

本頁保留原 plan 階段的研究基準與當時未驗事項。2026-09-07 結算導覽需求取代 R09 的原關重試描述，最新來源見 [結算決策](decisions.md)；沒有新增技術依賴或研究未知。

**研究範圍**：依 [規格](spec.md)、[數值表](balance.md) 與憲章 1.3.0，確認現有程式的改造位置、可沿用能力及新契約。本階段沒有修改遊戲程式。

研究後使用者補充 GitHub 操作統一使用 gh CLI，憲章升至 1.4.0；最終 plan 已增加原則 VIII 檢查。本機 gh 2.98.0 可用，本次研究未對 GitHub 進行遠端寫入。

## 研究前憲章關卡

產品範圍已定案，16 項規格品質檢查通過；沿用純規則／呈現分離、隔離保存與真實驗收要求。分支及功能指標均為 002，沒有掛鉤設定。研究不新增服務、技術堆疊或資料遷移，沒有需以例外放行的憲章違反。

## R01－沿用已安裝引擎與測試環境

**決策**：保留專案 `.venv`、Python 3.12.x、Ursina 8.3.0、Panda3D 1.10.16 與現有全部固定依賴，規則與測試使用標準庫。不新增 pytest、資料庫或外部後端。

**理由**：本機實測 Python 3.12.13、Ursina 8.3.0、Panda3D 1.10.16、Pillow 12.3.0；`pip check` 退出碼 0。以臨時保存根目錄執行 `unittest discover -s tests -q`，82 個既有測試於 0.468 秒全部通過、退出碼 0。這是 001 程式基準，不是 002 驗收。

**替代方案**：換引擎或升級套件會擴大本次風險，需求不需要；不採用。正式依賴仍以 [requirements-game.txt](../../requirements-game.txt) 為唯一版本清單。

## R02－目錄與武器身分取代槽位條件

**決策**：新增純規則 `catalog.py` 與 `loadout.py`；W01～W20、A01～A06、T01～T03 為穩定商品 ID。五槽只包含武器 ID／空值；當局開始時建立不可變的有效能力與配置快照。

**理由**：[config.py](../../air_defense/config.py) 使用五組平行陣列；[state.py](../../air_defense/state.py) 的選槍與射擊、[scene.py](../../air_defense/scene.py) 的模型及鏡頭、[audio.py](../../air_defense/audio.py) 的音效、[ui.py](../../air_defense/ui.py) 的 HUD 都依固定槽號判斷武器。只擴增陣列會把武器種類、配置位置與所有權混為一談。

**替代方案**：不保留舊五槽作隱藏對照層，也不將 20 種武器各寫一份控制器。商品使用唯讀定義、能力使用共同解析函式、射擊依模式分派。

## R03－發射、命中與固定步輸入分開

**決策**：新增 `weapons.py` 處理每武器彈匣、換彈、點放與發射排程；`combat.py` 保留鎖定、命中及傷害。輸入保存有順序的按下／放開／換彈／切槽事件，持續移動與視角另傳；120 Hz 固定步一次消費離散事件。

**理由**：目前 `validate_attack` 將無目標當成不可發射，不能支援射空扣彈。`InputFrame` 只有一次按下旗標，`main.py` 不傳持續開火；直接加布林 OR 合併會丟失同一固定步前的按下／放開順序。連射使用絕對模擬到期時刻累加間隔，避免 0.06 秒被每發捨入為 0.0667 秒。

**替代方案**：不使用引擎延遲回呼排程傷害；不以實際時間補算暫停。保留目前最大追算步數，低於可追算幀率時只比較有效模擬時間的攻擊量。

霰彈來源需包含 `shot_id` 與 `pellet_index`，避免現有每步來源／敵人去重吞掉同發其餘彈丸。狙擊射線改用有效射程，取消目前 `ray_target` 180 的硬上限。

## R04－火箭掃掠與碰撞表面爆炸

**決策**：新增 `projectiles.py`，以純規則線段掃掠處理火箭首次碰撞；防空 `Missile` 保留追蹤，加入發射時傷害與來源快照。地面、世界 AABB 與敵人受擊包絡皆共用世界資料。

**理由**：目前 RPG 於 `state.py` 直接在敵人中心扣血，不能呈現飛行時間。可沿用 [entities.py](../../air_defense/entities.py) 的 `ray_box` 與向量計算，但需加入碰撞法線與地面平面。爆炸在牆面直接驗可見性會在距離零碰回同一牆，必須以法線外推微量位置作遮擋查詢。

**替代方案**：不以動畫假裝投射物；不讓 Panda3D 碰撞回呼成為另一套傷害權威。同距離世界碰撞優先，爆炸按真正接觸點計半徑，僅可見性起點外推。

## R05－關卡成長與具名飛行參數

**決策**：建立 `DifficultySnapshot`，以 a、b 算生命與飛行倍率，出生時寫入最大生命、接近時間、轉向速率與最大偏航偏角。用十進位數值算倍率及向上取整，再轉為模擬數值。

**理由**：現有 `Enemy.max_hp` 固定 3／10；`AIRCRAFT` 第六數值被當成俯仰速率，而新版數值表明定為偏航偏角。必須拆為具名欄位，偏航相對朝城市的基準航向限制；偏航與俯仰的角速度均受表列最大轉向速率限制。

**替代方案**：不只改倒數時間或乘上重生次數；不把 FAST 強行加入既有編隊。FAST 以固定驗收情境測試，正式編隊維持既定公式。

## R06－保存 v2 與可重試交易

**決策**：保留 `SlotRepository`、純交易候選資料及 `pending_save` 流程，改用獨立 v2 根目錄與 `AIR_DEFENSE_V2_SAVE_DIR` 環境變數。新的嚴格型別保存裝備庫、個別武器、自訂、逐台砲塔、確認配置及操作歷史，不保存可推導的 A 與升級上限。

**理由**：目前 [save_data.py](../../air_defense/save_data.py) 已具 UTF-8、嚴格欄位、原子替換與備份，82 基準測試包含保存回歸；另起持久化技術無益。新環境變數避免沿用 v1 設定指向舊資料。

**替代方案**：不升級舊檔、不共用 schema、不把購買歷史當裝備庫重建。保留歷史跨重生；請求附檔案身分與輪次，先查操作指紋再驗輪次，防止延遲的上輪請求新增商品或重生資格。

保存失敗保留完整記憶體候選及原磁碟檔；阻擋後續變更，重試只寫同一份資料。配置須保存成功才可建當局；若確認配置保存失敗，重試成功回確認畫面，不自動進入戰鬥。

## R07－準備、鳥瞰與共用幾何

**決策**：新增 `deployment.py` 純幾何規則，`preparation.py` 管理草稿；使用目前 Ursina 相機切正交鳥瞰，退出時還原透視與第一人稱狀態。共用同一份世界包絡、路線與範圍規則，部署及戰鬥均以水平射程驗塔。

**理由**：目前塔是固定六位置且用三維距離，不能直接沿用。Ursina 安裝版本的 `camera.py` 確有正交切換及 film size 行為；本機 `OrthographicLens.extrude` 無視窗探測成功。正交投影與螢幕點轉射線的能力亦見 [Panda3D 正交鏡頭文件](https://docs.panda3d.org/1.10/python/programming/camera-control/orthographic-lenses) 與 [Lens.extrude 文件](https://docs.panda3d.org/1.10/python/reference/panda3d.core.Lens)。

**替代方案**：不使用 EditorCamera 的自由旋轉，也不引入地圖編輯器。新 UI 只提供已規定平移、縮放與放置；滑鼠點經鏡頭轉世界射線後，交由純規則平面交點及合法性檢查。

## R08－程序化美術、預覽與效果回收

**決策**：新增 `visual_catalog.py` 與 `models.py`，以可重用圓角盒、球／膠囊、圓柱及圓盤 Mesh 組合原創角色、裝備與城市；同一工廠供卡片預覽、第一人稱與世界物件使用。武器各有具名兩項輪廓差異，不以換色充數。

**理由**：既有模型全在 `scene.py`、配色為軍事風；可沿用材質隔離、幾何合併及效果池，新增固定部件配置。Ursina 的 [Mesh 官方參考](https://www.ursinaengine.org/api_reference.html) 與本機 `mesh.py` 提供頂點、法線及重建能力；不需增加建模依賴。

**替代方案**：不使用附件圖片作模型資產，不依賴外部下載或生成影像服務。保留已隨包 Noto 字型與自製 WAV，增加射擊模式及換彈音效映射。

每個可見發射來源保留至少一條短時曳光／槍口回饋，額外爆炸粒子才受低畫質效果預算限制；不能讓現有效果池已滿時整把武器完全沒有子彈效果。模型快取與活動物件分別量測。

## R09－回歸基準、工具與交付

**決策**：保留仍適用的保存、暫停、世界碰撞及戰役測試，按契約對照替換舊五槽、瞬間 RPG、共享升級、重生保留與六塔測試。更新現有 engine/performance probes 的 v2 固定資料與輸入入口。

**原設計理由（2026-09-06 歷史）**：`AppState.settle` 當時失敗 cursor 回 1-1，原新版要求原小關重試（已由 2026-09-07 決策改為敗北回 1-1）；舊保存測試將版本 2 當未知，也必須更新。現有性能工具硬寫槽 5 及六塔，不能直接作新版證據。

**替代方案**：不保留兩套執行中遊戲或刪除全部舊測試；只依 [契約替代對照](decisions.md) 修改衝突斷言。新增測試驗公開行為與時間／碰撞／交易邊界，不以函式名稱存在作完成證據。

## 研究結論與限制

所有設計所需技術選擇已解決，可進入資料模型及契約階段。已執行的是依賴相容性、正交鏡頭 API 探測與 82 項既有測試；沒有執行新版視窗、實際輸入、商品可玩性、FPS 或新資產驗收。這些仍是 implement／converge 的必要關卡。
