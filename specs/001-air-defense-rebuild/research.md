# 3D 防空守衛研究紀錄

**日期**：2026-09-05
**功能**：[spec.md](spec.md)

本文件記錄 plan 階段針對技術未知、依賴、整合方式與交付風險的決策。研究只處理如何可靠地滿足已核准的需求，不改變玩法契約。

## 決策 1：使用 Python 3.12.x、Ursina 8.3.0 與 Panda3D 1.10.16

**決策**：正式遊戲環境固定使用 Python 3.12.x，依賴檔直接固定 `ursina==8.3.0` 與 `panda3d==1.10.16`；其他 Python 套件只有在確實需要時才加入並固定版本。

**理由**：

- Ursina 8.3.0 的 PyPI 元資料（metadata）要求 Python >=3.12，且 2025-12-06 有穩定發佈的 wheel 套件。
- Panda3D 1.10.16 的 PyPI 檔案列出 Windows x86-64 的 CPython 3.12 wheel，能對應目標 Windows 桌面。
- Ursina 官方安裝頁以 Python 3.12 或更新版本為起點；選 3.12 可避免目前工作區的 Python 3.14.6 與尚未驗證的引擎組合成為必要風險。
- 目前 `.tools/spec-kit` 的 Python 3.14.6 沒有 Ursina、Panda3D 或 pytest，且沙盒直接連 PyPI 失敗；這是環境驗證限制，不代表依賴不可安裝。實作階段在可用網路／快取環境中執行實際安裝與圖形冒煙測試。

**考慮過的替代方案**：

- Python 3.14：Panda3D 已列出部分 3.14 Windows wheel，但遊戲依賴組合尚未在本機驗證，且不比 3.12 提供需求上的收益。
- Ursina GitHub 開發版：官方說明提醒開發版可能包含破壞性變更；正式重建先使用穩定 PyPI 版。
- 其他引擎：會改變附件指定的 Python 桌面技術方向，沒有產品收益足以抵銷重建成本。

**來源**：

- https://pypi.org/project/ursina/（版本、Python 需求、依賴與授權）
- https://www.ursinaengine.org/installation.html（Python 3.12.x 安裝基準）
- https://pypi.org/project/Panda3D/（Windows CPython 3.12 wheel）

## 決策 2：規則核心與引擎適配分層

**決策**：將狀態、關卡、經濟、武器合法性、傷害、鎖定、回血與存檔驗證寫成不匯入 Ursina 的純 Python 模組；`scene.py`、`ui.py`、`audio.py` 與 `main.py` 只負責引擎、輸入、呈現與生命週期適配。

**理由**：

- T01～T22 需要固定亂數、受控時間、精確邊界與無視窗測試。
- 單一當局狀態來源可以避免 HUD、實體和永久資料各自維護 HP、冷卻或彈藥。
- 引擎缺失、音訊不可用或著色器不支援時，可以由回退層保留規則測試與最小可玩流程。

**考慮過的替代方案**：

- 以單一 Ursina controller 維護所有資料：開發初期較快，但會使交易重送、暫停與純規則測試難以重現。
- 將規則放入多個 Entity 腳本：視覺物件刪除或重建時容易留下第二份狀態與延遲回呼。

## 決策 3：受控固定時間步與事件識別

**決策**：引擎每幀只把時間交給模擬時鐘；純規則以固定 1/120 秒步更新，單幀最多處理 8 步，超過部分丟棄並記錄受控 dt；所有 attempt、operation、projectile 與當局事件使用唯一 ID。

**理由**：

- 1/120 秒可在 4 秒下降、0.75 秒鎖定衰減與 0.20 秒砲塔冷卻上提供可重現的邊界精度。
- 最大步數避免失焦或低 FPS 後出現 spiral of death；暫停時不累積時間。
- 固定 ID 可讓舊局延遲回呼在新局被拒絕，並讓命中／壽命同幀事件只結算一次。

**考慮過的替代方案**：

- 直接以每幀 dt 更新所有物件：實作簡單，但高速導彈掃掠、長時間低 FPS 與暫停恢復會出現不可重現差異。
- 完全固定 1/60 秒且不限制追趕：在窗口失焦後可能一次執行過多步，造成卡頓與不公平傷害。

## 決策 4：碰撞與命中採雙層契約

**決策**：世界碰撞使用 Ursina/Panda3D 的 box、mesh 與 raycast；武器規則另保存邏輯上的目標包絡、水平／三維距離起點與 target_id。導彈以上一位置到下一位置的線段掃掠，地面武器以鏡頭中心射線取得目標後再次驗證規則。

**理由**：

- 引擎 collider 能阻擋玩家與敵兵穿越實體掩體；邏輯包絡能確保命中子模型解析到穩定敵人 ID。
- 依需求分開水平距離、三維距離與射線長度，避免用模型大小或準心放寬 12／32／180 的邊界。
- 線段掃掠避免 90 世界單位／秒的導彈穿透薄目標；命中優先於同幀到期。

**考慮過的替代方案**：

- 只以 Entity bounds 或單幀位置判斷：高速投射物與人物子模型會漏判。
- 只以 UI 準心判定命中：會把瞄準提示錯當成實際遮擋與射程。

## 決策 5：JSON 原子保存與可復原錯誤處理

**決策**：正式欄位保存於 `%LOCALAPPDATA%/AirDefenseQuality/slot-1.json` 至 `slot-5.json`；以 UTF-8 JSON、`schema_version`、嚴格欄位驗證、同目錄暫存檔與 `os.replace` 完成原子替換。載入壞檔先保留原始位元組並建立帶時間戳的備份，再讓玩家確認重建；測試透過注入的暫存目錄。

**理由**：

- Python venv 與存檔均應是可重建、可隔離的本機資料；不把暫時當局物件或 `pickle` 放入永久資料。
- 同目錄替換降低跨磁碟或中斷寫入留下半份 JSON 的風險；保存失敗時記憶體狀態仍可重試。
- 讀取 JSON 只接受明確 schema 與範圍，避免未知欄位或無效數值改變經濟和關卡。

**考慮過的替代方案**：

- 直接覆寫正式檔：電源中斷可能破壞唯一進度檔。
- pickle 或保存完整物件圖：不可移植、難以驗證且會引入不必要的反序列化風險。
- 將存檔放在專案目錄：可攜但會污染交付包，也可能與不同電腦的程式權限衝突。

**來源**：

- https://docs.python.org/3.12/library/json.html（標準 JSON 解析與不可信資料注意事項）
- https://docs.python.org/3.12/library/venv.html（虛擬環境隔離、不可搬移與可重建原則）

## 決策 6：使用自製程序化資產與自合成 WAV，外部資產只作明確授權回退

**決策**：第一版使用多部件幾何、材質層次、粒子與標準 WAV 生成器完成四種飛機、人物、Boss、武器、場景與聲音；若加入外部字型或素材，放入 `assets/` 並在 `LICENSES.md` 記錄來源與授權。繁體中文使用隨包提供且授權清楚的字型，不能把缺字方框當成回退。

**理由**：

- 附件不提供私人 STL／OBJ，程序化資產能在無外部下載時保留可玩性與可攜性。
- 多部件輪廓與每實例材質可直接驗證四種飛機、人物正面與武器辨識，不必依賴未驗證模型。
- 自合成 WAV 避免音效授權與缺檔造成啟動失敗；聲音仍可由音量設定控制或靜音。

**考慮過的替代方案**：

- 只使用單色方塊：不符合品質契約與正常距離辨識要求。
- 未查證網路資產：會把授權和離線啟動變成不可控依賴。
- 以系統字型為唯一方案：跨電腦可能缺少繁體中文字形。

## 決策 7：啟動器採專案 `.venv` 與明確 Python 路徑

**決策**：`start_game.cmd` 從自身目錄解析專案根，尋找可用 Python 3.12.x，在專案 `.venv` 建立環境，使用該環境的 `python.exe -m air_defense.main`；依賴版本未變時直接啟動。`run_tests.cmd` 使用同一 Python 執行測試與語法檢查，永不依賴 PowerShell 執行政策或系統 PATH 修改。

**理由**：

- Python 官方文件指出 venv 是隔離、可重建且不應提交的環境；使用明確解譯器不需要 activate。
- 以啟動器目錄解析路徑能支援中文與空白路徑，也避免從其他工作目錄啟動時找不到資產。
- Ursina 官方建置說明可產生 build 目錄與批次檔，但本產品先提供透明的來源啟動器，減少打包工具與原生視窗診斷的不確定性；可攜 ZIP 排除 `.venv`，讓新電腦重建。

**考慮過的替代方案**：

- 依賴全域 Python：會污染其他專案並在不同電腦產生版本漂移。
- 啟動時永遠重裝依賴：無網路時失敗且浪費時間。
- 直接提交 `.venv` 或單檔 exe：虛擬環境不可搬移；exe 打包會把圖形與資產錯誤藏在難診斷的包裝層。

**來源**：

- https://docs.python.org/3.12/library/venv.html（虛擬環境與 Windows 啟動方式）
- https://www.ursinaengine.org/building.html（Ursina build 的限制與選項）

## 未決風險與處理方式

- **本機網路／套件快取**：目前沙盒無法連 PyPI，因此尚未聲稱 Ursina 已安裝。實作的第一個環境任務必須在可用網路或預先快取中執行依賴安裝、匯入檢查與最小視窗冒煙測試；失敗時保留純規則成果並在 ACCEPTANCE 明確標記。
- **圖形裝置與原生視窗自動化**：純規則與無視窗冒煙測試可先完成；指定解析度、輸入、截圖與 FPS 必須在可開啟原生視窗的驗收環境實測，不能以單元測試代替。
- **公開 GitHub 遠端**：目前 `gh auth status` 顯示 token 無效；本地 `NEW--3d-game` 倉庫與 SDD 不依賴遠端，推送前需重新驗證認證。

## 第 0 階段：關閉決策

以下決策把獨立審核發現的未知轉成第 1 階段的固定契約：

1. **跨重啟冪等交易**：Profile v1 增加 `operation_history` 陣列，每筆保存 `operation_id`、`kind`、要求 fingerprint、結果碼與套用後的 profile revision；不設會破壞冪等性的淘汰上限。相同 ID 與相同 fingerprint 重送時回傳既有結果；相同 ID 但內容不同時回傳 `operation_conflict`，兩者都不改資料。每次 Profile 與 history 一起以同一個暫存檔原子提交。
2. **結構描述（schema）版本策略**：目前只接受 schema 1；未知版本、缺欄位、錯型別與未知頂層欄位拒絕載入，先保存原始位元組為 `slot-N.corrupt.YYYYMMDDTHHMMSSZ.json`，再由玩家確認是否重建。未來資料遷移必須以明確版本升級器與新驗收案例加入，不能在 v1 靜默猜測。
3. **隨機與戰役**：`attempt_id` 產生 `Seed(attempt_id, level_id)`，分成固定的 `aircraft_rng`、`drop_rng`、`ai_rng`；同一來源飛機的普通敵兵 0～3 只在其擊落事件抽樣一次，並以穩定 aircraft ID 順序消耗亂數。`boss_count` 只計裝甲 Boss 飛機，不重複計其產生的地面 Boss。
4. **商店效果**：升級目錄以附件公式固定：HP `100+10L`；鎧甲每級減傷 L、最少扣 1；鎖定時間 `max(0.1,3-0.15L)`；白框倍率 `1+0.10L` 且普通／多目標共用；輔助瞄準只在開鏡生效且每秒最多 3 度；全武器／砲塔冷卻倍率 `max(0.50,1-0.05L)`；容量每級加一台、最多 6 台並需先解鎖砲塔。各商品前置、上限、快捷鍵與錯誤碼在資料模型／UI 契約固定。
5. **固定步與事件優先序**：每幀將原始 dt clamp 到 `[0,0.1]` 加入 accumulator；每幀最多執行 8 個 1/120 秒 tick，超過部分丟棄並記錄。每 tick 順序固定為輸入佇列與冷卻更新 → 飛機移動／撞城／下降批次 → 敵兵移動／AI → 已存在導彈移動與掃掠 → 玩家與砲塔攻擊請求 → 依事件序列套用命中／傷害 → 敵人攻擊玩家／城市 → 完成／失敗判定 → ID 排序清理。導彈同 tick 命中與到期時命中優先；每個 target_id 每 tick 至多套用一次同源傷害。
6. **碰撞測試固定資料**：玩家使用半徑 0.45、高 1.8 的膠囊近似，移動速度 6、跳躍高度 1.5；人物瞄準包絡為中心對齊的 0.8×1.8×0.6 box。敵兵只在附件六個路點之間的可通行走廊移動，走廊與掩體 box 預先驗證不相交；飛機撞城以其 swept segment 與目標大樓 collider 相交或接近 `(0,10,-60)` 的 10 單位攻擊球判定。射線先受世界 collider 遮擋，再映射到目標包絡。
7. **效能與清理門檻**：暖機 10 秒後連續量測 60 秒；A=4 中畫質 1280×720 的平均 FPS 必須 >=55、P1（最差 1%）frame time 對應 FPS 必須 >=45，且不得有連續兩個以上 frame time 超過 250 ms 的持續卡頓。A=8 壓力場景連續量測 60 秒、以 1 秒取樣檢查投射物／特效活動計數不呈單調增加，並與十次生命週期一同記錄實體、更新任務、投射物、特效與輸入回呼計數，結束值與基準值差異必須為 0（允許一次性資源快取不超過固定常數）。
8. **測試執行器**：純規則與整合測試使用 Python 標準庫 `unittest`、`compileall` 與自製故障注入測試固定資料，不把 pytest 加入遊戲依賴；這讓 `run_tests.cmd` 在只安裝遊戲依賴的環境仍能驗證核心契約。若後續引入第三方測試執行器，必須另行固定版本並更新啟動契約。
