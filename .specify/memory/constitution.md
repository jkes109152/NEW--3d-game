# 3D 防空守衛專案憲章

## 核心原則

### I. 產品契約一致性

附件規格、核准的功能規格與驗收案例是產品行為的來源。實作必須保留核心玩法、
數值、輸入、戰役、存檔與重生契約；任何會改變玩家結果的例外必須先記錄在決策文件，
並同步更新規格與測試。範圍外的多人、登入、廣告、伺服器、付費商品與開放世界不得
偷偷加入。

使用者明確核准的產品改版必須建立新版功能規格與逐項契約對照；新版只取代對照中
明列的舊行為，未取代部分仍依原契約驗證。歷史規格不得改寫為新版已實作的證據。
使用者選擇新版本從零開始時，必須使用獨立保存位置並保留舊資料，不得暗中搬移、
轉換或清空舊版存檔。授權調整數值時，必須在實作前列出完整數值及可驗證效果。

### II. 先建立可決定規則

關卡生成、經濟、命中、傷害、回血、交易、存檔驗證與狀態轉移必須位於可在沒有圖形
視窗時獨立執行的規則模組。時間、亂數、存檔路徑與外部能力必須可注入或替換，
使邊界案例可重現；畫面、音效與引擎適配層不得成為規則的第二個真相來源。

### III. 以證據驗證品質

每個需求必須有可執行的測試、整合情境或真實畫面證據。測試先覆蓋公開行為與邊界，
再覆蓋引擎整合；驗收報告只能將實際執行且通過的項目標為通過。效能、輸入、畫面、
音效與資源清理不得只以程式碼檢查推論完成。

### IV. 安全持久化與冪等操作

玩家資料必須以嚴格驗證的 UTF-8 JSON 與原子保存保護，測試資料與正式資料必須隔離。
購買、獎勵、重生、保存與延遲事件必須有唯一操作或當局識別，重試不得重扣、重發、
重生或污染新的一局。損壞資料、寫入失敗與未知版本必須保留可復原證據並清楚告知玩家。

### V. 可用品質與誠實回退

遊戲必須在指定解析度、中文路徑、無音訊裝置、缺少可選資產與降低畫質設定下仍能
啟動並完成核心流程。繁體中文文字、可辨識的模型、碰撞公平性、暫停／失焦保護與
可理解錯誤訊息是交付品質的一部分；回退能力不得隱藏缺失或假稱驗收成功。

### VI. SDD 文件繁體中文化

所有 SDD 文件必須以繁體中文（台灣）撰寫，包括標題、段落、表格、註解、需求、
計畫、研究、任務、資料模型、契約、清單、決策與驗收報告。每個 SDD 階段完成前必須
檢查新增或修改的文件，確保說明文字沒有改用簡體中文或未經說明的其他語言。程式碼
識別字、命令、檔案路徑、套件名稱、API 名稱、協定欄位與必要的外部原文可保留其
標準拼寫；其周圍的解釋仍必須使用繁體中文。

### VII. Spec Kit 分支命名與 PR 收尾

所有工作分支必須遵循本專案 Spec Kit 的流水號命名模式 `NNN-short-name`，例如
`001-air-defense-rebuild`。`NNN` 為至少三位數、不足補零的功能編號；`short-name`
使用小寫英文字母、數字與連字號，清楚描述工作目的。新增功能編號必須依
`.specify/init-options.json` 的 `feature_numbering: sequential` 設定與既有 `specs/`
目錄遞增配置，並在建立分支前核對本機與遠端分支，避免編號或名稱衝突；既有功能的
後續工作沿用其功能編號，並保留分支與規格的對應關係。工作分支不得額外加上
`codex/`、`feature/` 或 `fix/` 等前綴；`main` 等長期整合分支維持既有名稱。

工作成果必須推送工作分支並發送 PR，透過 PR 合併至預期的目標整合分支；PR 必須記錄
變更目的、適用的規格連結與實際驗證結果，通過既定品質關卡及必要審查後才可合併。
不得以直接推送整合分支取代 PR 流程。必須確認遠端 PR 的狀態為已合併，且交付變更
確實納入預期目標分支；PR 已建立、已核准或已關閉均不能單獨作為合併成功的證據。

確認合併成功後，必須清除該工作分支的本機與遠端分支，並更新失效的遠端追蹤參照。
清除前必須確認分支上沒有尚未納入合併的新增提交，也沒有未保存的工作；不得刪除
未合併的工作、長期整合分支、規格目錄或驗收證據。若合併狀態無法確認或清除失敗，
必須保留尚未確認可刪除的分支並記錄原因，不得宣稱收尾完成。

### VIII. GitHub 操作統一使用 gh CLI

所有與 GitHub 遠端有關的查詢及變更，必須透過 GitHub CLI `gh` 執行，包括倉庫、
遠端分支與提交、Issue、PR、審查、檢查結果、Actions、Release、合併及遠端分支清理。
優先使用對應的 `gh` 原生命令；原生命令未涵蓋的 GitHub 能力必須使用 `gh api`。
不得改用瀏覽器操作、GitHub 連接器、直接 HTTP／SDK 呼叫或直接 Git 遠端指令繞過。

本機 Git 操作仍使用 `git`，包括 status、diff、branch、switch、add、commit、log 與
本機合併；涉及 GitHub 的遠端存取必須由 `gh` 原生命令或 `gh api` 完成。
`gh` 自身內部使用的 Git 傳輸不受此限制，但不得建立包裝其他工具的別名來規避規則。

執行前必須確認 `gh` 可用、目標倉庫及所需認證；不得輸出權杖或秘密。操作後以
`gh` 的退出碼及結構化結果核對遠端狀態；PR 合併與清理仍須滿足原則 VII 的證據要求。
`gh` 缺失、認證不足或所需操作無法完成時，保留工作並記錄具體原因，不得靜默換工具
或宣稱成功。此工具約束不增加任何未經使用者授權的遠端寫入權限。

## 工程約束

- 目標平台為 Windows 桌面，正式遊玩離線；依賴必須置於專案自己的虛擬環境，
  不污染系統 Python。
- Python 3.12.x 與 Ursina／Panda3D 是技術基準；plan 階段固定實際可安裝版本，
  並保留不依賴引擎的純規則測試。
- 資產、字型與音效必須隨包提供或有精確授權記錄；不得依賴私人模型、秘密憑證、
  遠端服務或啟動時網路。
- 啟動器、測試入口、文件與畫面文字使用繁體中文；識別字、套件名稱與檔名可使用英文。
- SDD 產物與 `docs/` 交付文件遵守原則 VI；保留必要的程式、命令、路徑與協定原文時，
  必須在繁體中文說明中提供語意。
- 002 改版採全遊戲糖果色與圓潤造型，保留第一人稱空地防守；武器改為 20 種武器池，
  裝甲為 6 種，砲塔為 3 種。重生清除全部已購成長與裝備，再配發免費基礎武器；
  詳細商品、出戰、重生及新版資料隔離規則由 `specs/002-gameplay-expansion/spec.md` 定義。
  此為使用者已核准的產品改版，不受 001 的永久升級或軍事美術描述限制。

## 開發流程與品質關卡

- 工作順序為 constitution → specify → clarify（若需要）→ plan → tasks → implement →
  converge；每個階段的輸出必須成為下一階段的輸入。
- 分支建立與 PR 發送前必須檢查原則 VII 的命名格式、功能編號及規格對應；不合規時
  必須先修正分支名稱及受影響的文件引用。
- GitHub 遠端檢查、交付與收尾必須遵守原則 VIII；使用 `gh` 核對倉庫、分支與 PR，
  優先取得 JSON 結果。多行 PR／Issue 內容以檔案搭配 `--body-file`，API 請求以
  `gh api --input` 傳入結構化資料，避免 shell 插值破壞內容。
- 計畫（plan）在研究完成前不得保留未解決的技術未知；設計完成後必須重新檢查本憲章，
  任何違反都要記錄理由與替代方案。
- 商品數值、個別武器升級、配件取捨、敵人成長與重生經濟必須在規格階段建立可驗證
  表格；plan 與 tasks 必須承接這些表格。實測需調整時，同步修訂規格、決策與驗收，
  不得將未定義數值交由實作階段自行猜測。
- 實作（implement）每完成一批變更必須重跑受影響測試；視覺、輸入、效能與交付檢查須保留
  真實路徑、指令、退出碼或截圖。
- 憲章（constitution）、規格（spec）、計畫（plan）、研究（research）、任務（tasks）、契約（contracts）、清單（checklists）與驗收文件完成前，
  必須通過繁體中文文字檢查；語言不合規時不得通過該階段關卡。
- 複雜度只在需求契約或公平性要求確實需要時增加；每個額外服務、全域狀態或特殊回退
  必須在 `docs/DECISIONS.md` 說明原因。
- 交付必須依序完成推送工作分支、發送 PR、通過檢查與審查、確認 PR 已合併，最後清除
  分支。PR 記錄必須能追溯目標分支、合併結果與驗證證據；採 squash 或 rebase 合併時，
  必須核對 PR 記錄及變更是否已納入目標分支，不得只以提交祖先關係判斷。
- 清除分支前必須切換至目標整合分支並同步遠端最新內容；若工作分支仍由其他工作樹
  （worktree）使用，必須先確認該工作樹沒有未保存或未交付的工作，再安全解除使用。
  完成後必須核對本機與遠端工作分支均已不存在，並回報 PR 連結、合併結果及清除結果；
  遠端自動刪除分支後仍須完成本機清理，任何未完成項目都必須明確列為待辦。

## 治理

本憲章優先於未明確核准的慣例。新增、移除或重新定義原則時，必須在同一變更中更新
版本、同步影響報告、受影響規格與遷移／驗收說明；單純文字澄清可升 patch，
新增原則或重大治理範圍升 minor，破壞既有治理契約升 major。每次 plan、tasks、implement
與 converge 都必須檢查遵循情況；未通過的關卡必須停止相關階段或明確記錄阻擋原因。
每次 PR 審查必須核對本憲章、命名要求及 gh 使用紀錄；合併收尾必須依原則 VII、VIII
檢查合併證據、本機與遠端分支的清除結果及遠端操作工具。
